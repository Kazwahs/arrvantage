# arrVantage — Project Context

A unified web dashboard for a self-hosted media automation stack (Radarr/Sonarr/Lidarr/Chaptarr, Plex/Jellyfin/Emby, Prowlarr, qBittorrent/SABnzbd, Overseerr/Jellyseerr, Tdarr). Single Flask app, single container, no database — built collaboratively with Claude over an extended project. This file exists so Claude Code starts with real, hard-won context instead of rediscovering it.

## Architecture

- **`app.py`** — the entire backend, single file, Flask + gunicorn.
- **No database.** All config (instances, users, API keys) lives in one `config.json`, path controlled by `CONFIG_DIR` env var. Loaded once into module-level globals (`CONFIG`, `APPS`, `USERS`, etc.) at import time, mutated in place when Settings is saved.
- **Single gunicorn worker, deliberately.** This was a real bug fix, not an oversight — `CONFIG`/`USERS` are per-process in-memory state. With 2+ workers, completing the setup wizard on one worker left other workers still thinking no users existed, causing an infinite `/setup` ↔ `/login` redirect loop on fresh installs. Do not raise `--workers` above 1 without solving that properly first (e.g. moving shared state to the file/a real store).
- **CSRF via one global `before_request` hook**, not per-route decorators — covers every POST automatically. Frontend's global `fetch()` override attaches the token as `X-CSRF-Token` header for JS calls; traditional forms use a hidden field.
- **`/health` is the only endpoint safe for Docker/TrueNAS healthchecks.** `/login` and `/setup` both redirect depending on setup state, so neither is a safe target — this was a real production bug on the TrueNAS catalog listing before `/health` was added.
- **The main page is only a shell.** `index()` does no network calls - it renders the sidebar and Home from config. Each instance's panels (library, request, queue, history, system) come from `GET /fragment/instance/<name>` (`templates/partials/instance_panels.html`), fetched by `ensureInstanceLoaded()` the first time an instance is opened. Don't put per-instance data back into `index.html`; it used to ship every library in the page (multiple MB) and fetch everything serially before the first byte.
- **Independent external calls run concurrently** via `run_concurrently()` (shared `FETCH_POOL`, per-batch timeout, never raises - a failed call becomes `(False, "error text")`). Use it for any new endpoint that needs several upstream calls.
- **Home leads with `/api/attention`.** `summarize_attention()` (pure, unit-tested) merges the same warning across apps by health `source`, collapses a disk several apps share into one item, flags stalled/failed queue items and fully unreachable instances, and ranks critical before warning. The sidebar dot only appears for critical items or stalled downloads - never for a plain health warning. Results are cached ~30s (`?refresh=1` bypasses). It also checks the rest of the stack: `gather_attention()` probes every enabled downloader (`probe_downloader`), Prowlarr (`fetch_prowlarr_indexers`), media server (`probe_media_server`) and Tdarr, and hands the results to `summarize_attention(signals, services)`, which stays pure (see `_summarize_services`). Only outages are raised: a down downloader, indexer service or media server is critical, as is *every* enabled indexer failing (an arr app's own indexer warning that merely repeats those names is dropped); a down Tdarr is only a hideable warning because it is often off on purpose. Partial indexer failures and qBittorrent firewalled/disconnected are deliberately NOT raised (too noisy; the arr apps already name failing indexers and Home's Indexers panel lists them). The media server probe hits a public no-token endpoint (`/identity` for Plex, `/System/Info/Public` for Jellyfin/Emby) with one retry, so a limited API token can never make a running server look down - an earlier version reused the authenticated Now Playing call and reported a working Jellyfin as unreachable. Items carry a `service_type` so the Home link opens the right sidebar view. A failed probe makes the check `complete: false`, like a failed arr call. In the panel, criticals always show and warnings are folded behind a "Show N warnings" toggle (remembered per browser in `localStorage.arrAttentionWarnings`).
- **Home is a stack of keyed panels users can rearrange.** `#home-panels` holds one `.home-panel[data-panel=KEY]` per entry in `HOME_PANELS` (attention, comingup, downloads, libraries, mediaservers, indexers, transcoders); `loadHomeStats()` and `renderAttention()` only fill each panel's body, never replace the panels, so a user's order survives refreshes. The layout (`{"order": [...], "hidden": [...]}`) is stored per user as `home_layout` on their record in `config.json`, embedded in the page as JSON, and saved through `POST /api/home/layout` (`{"reset": true}` clears it). Everything passes through `normalize_home_layout()`, so unknown/duplicate keys are dropped and a panel added later appears at the end. `parse_users()` carries `home_layout` forward - Settings rebuilds every user from the form and would otherwise wipe it. The cards inside the libraries / media servers / indexers / transcoders panels can be ordered too: each `.stat-card` carries `data-card` (its name), the order is saved as `cards: {panelKey: [names]}` in the same layout (only present when set, capped, names unchecked on purpose so a renamed instance just falls to the end), and `cardOrder` in `index.html` is the source of truth rather than the DOM, because a panel's cards may not have loaded when something else is saved. Arrange mode gives each card a grip (pointer drag), Earlier/Later buttons and arrow keys; the card's contents go inert. A new card panel needs its key in `CARD_PANELS` and `CARD_PANEL_KEYS`. To add a Home panel: add its key to `HOME_PANELS`, a `<section class="home-panel" data-panel data-label>` in `index.html`, and fill its body from JS.
- **Coming Up is a Home panel (`comingup`) fed by `GET /api/coming-up?days=7|14|30`.** Sonarr (`series`), Radarr (`movie`), Lidarr (`artist`) and Readarr/Chaptarr (`author`) instances are asked for `/api/<v>/calendar?start&end&unmonitored=false` (`includeSeries` / `includeArtist` / `includeAuthor` too); the endpoints were checked against each app's CalendarController (Readarr: its published API client, which lists `start`, `end`, `unmonitored`, `includeAuthor` and a `BookResource` with `title`, `releaseDate`, `seriesTitle`, `author.authorName`, `statistics`), the response field names (`airDateUtc`, `inCinemas` / `digitalRelease` / `physicalRelease`, `releaseDate`, `artist.artistName`) were not checked against a live server. Chaptarr is a Readarr-compatible fork whose docs could not be read, so the `author` calendar is unverified against a real Chaptarr (`statistics.bookFileCount` for "already downloaded" is the least certain field). Kapowarr (`comic`) has no calendar and is not included. `calendar_items()` is pure and turns records into items: a timed episode keeps its UTC timestamp (the browser puts it on the viewer's local day), a date-only release is `all_day` and keeps its date, and each item carries its instance's `color`. The answer is cached 5 minutes only when no app failed. The panel colours each item's left bar with the instance colour, but every item also names its instance in words (colour is never the only signal). With two or more sources the legend is a row of toggle buttons (`.cu-toggle`, `aria-pressed`; switched off = hollow swatch + struck-through name, never colour alone) that filter the panel client-side from the last answer (`comingUpData`, no refetch); the hidden source names are kept per browser in `localStorage.arrComingUpHidden` (pruned to sources that still exist) - not per user on the server, on purpose, to keep it light. A single source stays a plain label. The selected range button uses the solid `--accent` / `--on-accent` pair - the washed `--accent-wash` + `--accent` combination failed contrast in two themes.
- **Downloads is a Home panel (`downloads`) fed by `GET /api/downloads`** (any signed-in user; a card per enabled downloader (qBittorrent, SABnzbd), polled by the page every `DOWNLOADS_POLL_MS` = 10 s, only while Home is showing in a visible tab; the server shares one answer for `DOWNLOADS_CACHE_SECONDS` = 5 s, `?refresh=1` bypasses). Verified against the clients' own API references: qBittorrent `torrents/info?filter=downloading` and `filter=stalled_downloading` (the docs do not define what each filter includes, so `qbt_downloads_view()` also checks `state`, de-duplicates by hash, and never lists paused/stopped/seeding/errored ones; `eta` 8640000 = none) plus `transfer/info` for the global speeds; SABnzbd `mode=queue&limit=30` (`kbpersec`, `status`, `paused`, `noofslots_total`, slot `status` / `percentage` / `timeleft`). The two view builders (`qbt_downloads_view`, `sab_downloads_view`) are pure and return the same card shape (`state` downloading/waiting/paused/idle, `down_speed`, `up_speed` (null for SABnzbd), `counts`, `total`, at most `DOWNLOADS_ITEM_LIMIT` `items`); failures are a few words from `short_request_error()` (never an address or body). `fetch_download_client()` runs its calls one after another on purpose - the clients are already fetched in parallel on the shared pool and a pool task waiting on its own pool can deadlock. It is read-only: pausing/removing stays in the Downloaders view (clicking a client's name opens it). A client that is down is already a critical item in Needs attention. The panel redraws every poll, so `renderDownloads()` puts keyboard focus back on the same client button; it is not an aria-live region (a 10 s update would be noise).
- **Settings has a "Backup, restore and diagnostics" group** (outside the main form, so it never affects the Save button). *Export* (`GET /api/config/export`, `?secrets=1` adds API keys and password hashes; `secret_key` is never exported). *Restore* is two calls to `POST /api/config/import`: without `confirm` it only returns a report (`plan_import()`, no side effects); with `confirm: true` it writes `config.backup-<utc>.json` (mode 600, newest `CONFIG_BACKUPS_KEPT` kept), saves, and goes live through `apply_config()` - the same in-memory refresh Settings uses, so use that for any new "replace the whole config" path. `plan_import()` validates everything (known types only, http(s) URLs, colours, bcrypt/scrypt-looking hashes, unknown fields dropped, at least one admin) and for a file saved without keys keeps the keys and accounts already set up. Preview text is built with `textContent`, never `innerHTML`, because names come from the uploaded file.
- **Diagnostics (`GET /api/diagnostics`)** describes the setup by type and count only - no names, URLs, keys or usernames - plus the last `RECENT_WARNING_LIMIT` warnings, which an in-memory logging handler collects whatever `LOG_LEVEL` is (the logger always lets WARNING through; the console handler applies the level). Server addresses are replaced by `jellyfin-1`-style labels unless the person untoggles it. The first line is the release (`APP_VERSION`, via `resolve_app_version()`) plus a hash of `app.py` that tells two builds of the same release apart. It also reports the monitor and alerts as counts (no names, topics, tokens or addresses).
- **The release number is `APP_VERSION` at the top of `app.py`. Bump it in the same commit as the release you are about to publish** (the image, the About panel, Copy diagnostics, the webhook payload and the GitHub release tag should all agree). `ARRVANTAGE_VERSION` in the environment overrides it if it looks like a version; the build workflow is protected, so nothing sets it today. It reaches the page as `app_version` and the About slide-over shows it.
- **A background monitor runs the Needs attention check on its own** (`start_monitor()`, one daemon thread of the single worker, started when gunicorn imports the module; `MONITOR_INTERVAL` seconds, default 60, `0` = off, clamped to 30-3600; the tests set `ARRVANTAGE_NO_MONITOR=1` in `conftest.py` and call `monitor_once()` directly; under `python app.py` with the reloader only the serving process starts it). Each check calls `gather_attention()` (so it shares the 30 s cache with page loads) and feeds the result to `track_incidents()`, which is pure: a problem is keyed by `incident_key()` (the item's `hide_key`, else its `id`, so a disk's changing reading is one problem), becomes an `opened` event after `MONITOR_CONFIRM_CHECKS` (2) sightings in a row and a `cleared` event after as many clear checks, and a check with `complete: false` cannot clear a warning (its call may be what failed) - only `unreachable` / `service` items, which are probed directly, can end then. `is_outage()` (service down, unreachable, or critical) decides what the history lists and what the "outages only" alert level sends. State (open problems plus the last 90 days / 500 outages) is `history.json` next to `config.json`, written atomically with mode 600 only when it changed, read back through `_clean_history_state()` (trust nothing), and survives a restart without re-announcing anything. `GET /api/history` is open to any signed-in account (it lists what Needs attention already shows them); the slide-over is `showHistory()` in `index.html`, opened from the History link beside the Needs attention heading.
- **Alerts are per administrator and the destinations are secrets.** An admin's `notify` on their user record is `{"level": "critical"|"all", "ntfy": {"server", "topic", "token"?}, "discord": {"webhook_url"}, "telegram": {"bot_token", "chat_id"}, "email": {"host", "port", "security", "mail_from", "mail_to": [...], "smtp_user"?, "smtp_password"?}, "webhook": {"webhook_url"}}`, cleaned by `normalize_notify()` (destinations are listed in `NOTIFY_CHANNELS`, which is also the order a message is sent in) (also used when reading config and imports). Only admins may have one - the server will POST to whatever address is typed in, so a regular account must never be able to set it (`deliver_events()` and `_import_users()` both enforce this). It is edited in **Settings > Alerts** through `/api/notifications` (GET never returns the topic, token or address - only whether each is set; a blank field on save keeps the saved value; `remove`/`clear_token` clear), tested with `/api/notifications/test`, stripped from exports unless "include keys" (`topic`, `token`, `webhook_url`, `bot_token`, `chat_id`, `smtp_user`, `smtp_password`, `mail_from`, `mail_to` are in `EXPORT_SECRET_FIELDS`; Discord reuses the `webhook_url` field name, so it is covered too. The email fields are named `smtp_user` and `mail_*` on purpose: `_strip_secrets()` removes a key by name anywhere in the export, and a plain `username` / `to` would have stripped the account names), kept across a Settings save by `parse_users()`, left out of the data the Settings page is rendered with, and never logged: `_post_json()` sets `_log_ctx.redact_path` so the request logger describes the call by host alone and drops the error text (a webhook's key lives in its path). A failure is shown and logged as words only (`HTTP 401`, `could not connect`...). ntfy is sent with its JSON publish (`POST <server>/` with the topic in the body - header titles can't carry non-Latin-1 text), webhooks get a JSON body (`event` = opened/cleared/test). **Discord is its own destination (`discord`)** because a generic JSON POST is not a message to Discord (it wants `content` or `embeds`): `send_discord()` posts one embed (title, description, a `Services` field, the incident time as `timestamp`, colour from `DISCORD_COLORS`, severity also in words in the footer: Critical / Warning / Resolved / Test) with `allowed_mentions: {parse: []}` so a service name like `@everyone` cannot ping anyone, and text cut to Discord's limits. The address is checked by `_clean_discord_url()` (https only, `discord.com` / `ptb.` / `canary.` / `discordapp.com`, the `/api[/vN]/webhooks/<id>/<token>` path, an optional `thread_id` query, no user name or port) both on save and when reading config or an import, so that box can only ever send to Discord. `send_discord()` rewrites `_post_json()`'s wording for Discord's causes (404 = the webhook was deleted, 401/403 = refused, 429 = rate limited, 400 = message not accepted; Discord answers 204 with no body on success). The message format follows Discord's webhook documentation (embed limits: title 256, description 4096, field value 1024) and the user has confirmed the Settings "Send a test alert" works against a real Discord channel (8 Nov 2026). **Telegram (`telegram`)**: `send_telegram()` POSTs `sendMessage` to `TELEGRAM_API` (`https://api.telegram.org`, fixed in the code, so that box can only ever reach Telegram) with the token in the path (`_post_json()` keeps the path out of the logs) and an HTML-mode text (title in bold, message, then italic severity and services; everything passed through `html.escape`, cut well under the 4096 limit, link preview off). The token is checked by `_TELEGRAM_TOKEN_RE`, the chat by `_TELEGRAM_CHAT_RE` (a number, negative for groups and channels, or `@channelname`). `find_telegram_chats()` (`POST /api/notifications/telegram-chats`, admin only, blank token = the saved one) calls `getUpdates` and lists the chats that have written to the bot (message, edited message, channel post, `my_chat_member`; newest first, at most `TELEGRAM_MAX_CHATS`), so nobody has to dig the chat id out of a URL; the labels come from other people's chat names, so the page sets them with `textContent`. `_telegram_words()` rewrites failures (400 = wrong chat or the bot has not been messaged, 401 = wrong token, 403 = blocked or removed, 404 = unknown token, 409 = the bot has a webhook set, 429 = rate limited). The Bot API calls and field names were taken from Telegram's published Bot API page, but only the Update / Chat objects and the response shape could be read in this session (the fetched copy cut off before `sendMessage`), so `sendMessage`'s parameters (`chat_id`, `text`, `parse_mode`, `link_preview_options`) and its 4096-character limit are from memory; it was tested only against a local stand-in - the Test button is how the user confirms it. **Email (`email`)**: per administrator, like the others. `send_email()` uses `smtplib` with `NOTIFY_TIMEOUT_SECONDS` per operation, `ssl.create_default_context()` (certificates are checked; a self-signed server fails with "the certificate was not accepted" - there is deliberately no "ignore certificate errors" switch), and one of three security modes from `SMTP_SECURITY` (`starttls` is the default, `ssl`, `none`); the login is optional (a mail server on the LAN often has none). `build_email()` is pure (subject `[arrVantage] Critical: <title>` / `Warning:` / the title for a recovery, which already starts with "Resolved:"; a plain-text body; `Auto-Submitted: auto-generated`; a line break in a title cannot add a header). The hostname is checked by `_MAIL_HOST_RE` (no scheme, path or port), addresses by `_MAIL_ADDRESS_RE` (ASCII only), at most `MAIL_MAX_RECIPIENTS` recipients. `_smtp_words(err, stage)` turns exceptions into words with no address, login or server reply (login refused, recipient refused, sender refused, security option not offered, connection closed, "answered 5xx", certificate, timeout, cannot find the server); `send_email()` tracks the step it is on (connecting, saying hello, starting encryption, logging in, sending the message) and the generic failures say it, e.g. "closed the connection (while logging in)". This was added after the user's first Gmail test failed with a bare "closed the connection" on port 465 although `smtplib.SMTP_SSL('smtp.gmail.com', 465)` worked by hand from inside the container; the cause was not yet known when it was written. The Settings test result for email also shows the server, port and mode actually used (`via`), so a stale saved setting is visible. `local_hostname` is `socket.gethostname()` because `getfqdn()` can stall on DNS. A save with a blank login or password keeps the saved one; `clear_login: true` removes both. `notify_view()` sends the server, port, security, sender and recipients (not secrets, and the form needs them) but only whether the login and password are set, and the security options as a LIST (a JSON object would be sorted by `jsonify`, putting STARTTLS last). Tested against a real local SMTP server (the `smtp_server` fixture in `Tests/test_alerts.py`, which offers `AUTH PLAIN`) for `none`, and with a fake `smtplib.SMTP` / `SMTP_SSL` for the STARTTLS and SSL steps; never against a real provider - the Test button is how the user confirms it. Slack, Pushover and Gotify were not built. Messages are written by pure functions (`compose_messages()`: more than `NOTIFY_MAX_SEPARATE` events in one check become one summary; `events_for_level()`: a warning the person hid on Home stays quiet, criticals cannot be hidden). The ntfy access-token header (`Authorization: Bearer`) and the JSON field names were checked against ntfy's source/docs; ntfy has since been confirmed working against a real ntfy server (the webhook path has only been tested against a local stand-in).
- **BookOrbit is a media-server type (`bookorbit`) with a health check and nothing else, on purpose.** Verified: `GET /api/v1/health` answers `{"status": "ok"}` with no sign-in (`fetch_bookorbit_health()`, one retry like the other probes, failures reported as a few words). Not verified, so not built: it has no documented API key or REST reference (Swagger is off unless `SWAGGER_ENABLED=true`); its API sits behind a JWT login (`POST /api/v1/auth/login`, which can be disabled - bookorbit issue #1321) and its OPDS feed (`/api/v1/opds`) uses separate HTTP Basic accounts. If a stable API appears, library counts / recently added are the next step - check the real responses first. Wiring: `probe_media_server()` feeds Needs attention (down = critical outage, same as Plex), the Settings Test button needs no token, the sidebar entry opens a one-tab Status view (`/api/bookorbit/health/<name>`) with an Open link, and `_dispatch_media_server_fetch()` / the rescan route refuse any type that is not Plex/Jellyfin/Emby (before this, a Komga server's Rescan button would have called Jellyfin's scan). No icon is set: `dashboard-icons` was not checked for a BookOrbit logo.
- **Librarr is an instance kind (`librarr`, `backend: "librarr"`, label "Manga and books (Librarr)")**: name, address and an `API_KEY` sent as `X-Api-Key`. It was a downloader type in the unreleased 1.4.0 build, and the user then asked for it under Instances (sidebar and Settings > Instances, a card in Home's libraries panel instead of Downloads). `migrate_librarr_downloaders()` moves any `downloaders` entry of type `librarr` into `instances` (name, address, key, colour and on/off kept; a clashing instance name gets " (2)"); it runs in `load_config()` (and saves the file) and in `plan_import()` (so a backup made before the move still imports, with a note). Checked against its README and a real Librarr 1.5.0 server (read-only calls through the person's signed-in browser; the header form of the key has not been tried against a real server, the Settings Test button is how it gets confirmed). Like Kapowarr, each of `fetch_queue/history/health/diskspace/library` starts with a `backend == "librarr"` branch. **Queue**: `GET /api/downloads` (`{"downloads": [{source, title, status, job_id, error, max_retries}]}`) -> `librarr_queue_items()` (pure; finished jobs dropped; a failed job has status `failed` and a message, so Needs attention flags it like Kapowarr; unknown progress is `None`, never 0%). Only a failed job was ever seen live, so `_librarr_group()` reads the other status words by meaning and treats an unknown word as downloading. Retry is `POST /api/librarr/retry/<name>/<job_id>` (the `searching` permission; ids must match `LIBRARR_JOB_ID`). **History**: `GET /api/activity` (`{"events": [{id, event_type, title, detail, job_id, timestamp}]}`) -> `librarr_history_items()` (newest first; `download_start` = Started, `*_import` = Imported; sign-in and settings events left out). **System**: `GET /health` needs no key (so a wrong key never makes a running Librarr look down) and gives a notice (version, sources on) or a warning when no source is on; there is no disk space (the heading is hidden). **Library**: `GET /api/library/manga?page=N` is 100 files a page and one item is one FILE (a series is many items sharing a title), so `fetch_librarr_library()` reads up to `LIBRARR_LIBRARY_MAX_PAGES` pages within `LIBRARR_LIBRARY_BUDGET_SECONDS` and `librarr_group_files()` makes one card per title (case-insensitive; `item_id` = lowest file id; file names, never paths, kept for the details window; no cover; status always Downloaded). If the list was cut short, `complete` is false: the page says so and Home leaves the size out. Home's libraries card says titles and files (`detail_text`), never "missing". Librarr only lists what it imported itself. Details: `/api/details/<instance>/<id>` -> `librarr_item_details()` -> `renderLibrarrModal()`. **Manga search** (the instance's Search tab, shown only with the `searching` permission; a Librarr instance has no Request tab): `GET /api/search/manga?q=` asks ~13 sources and took ~30 s on a real server, which would freeze the single gunicorn worker, so `POST /api/librarr/search/<name>` starts it on its own thread (`_run_librarr_search`, at most `LIBRARR_SEARCH_MAX_RUNNING`, the same query is shared, entries pruned after `LIBRARR_SEARCH_KEEP_SECONDS`) and the page polls `GET /api/librarr/search/<name>/<id>` every 1.5 s. Results are cut down by `librarr_search_results()` to title/source/size/seeders/score/in_library plus a token - a result's `download_url` can contain an indexer's API key, so the links stay on the server and `POST /api/librarr/grab/<name>/<id>/<token>` sends the stored result to Librarr's `POST /api/download` itself (`librarr_grab_body()` mirrors the body Librarr's own page sends, read from its JS: title, download_url, abb_url, source, source_id, md5, author, info_hash, magnet, media_type, download_protocol, force; the README's `/api/download/torrent` is not what its page uses). A 409 `already_in_library` becomes a "Send anyway" button (`force: true`). Search and grab are scoped to the user who started the search. The Search tab is not rebuilt when the queue refreshes: `refreshInstanceLive()` re-fetches `/fragment/instance/<name>` and swaps in only the queue, history and system panels (after Retry, Send, or the Refresh button). Not verified: a real download POST (tests use a fake; Librarr's own page was only read), the status words of running jobs, whether Librarr answers `limit` on `/api/activity`. The search is manga only; Librarr also has ebook and audiobook search (`/api/search`, `/api/search/audiobooks`) if that is wanted later. No icon is set (not checked in `dashboard-icons`).
- **Short in-process caches** (`_ATTENTION_CACHE`, `_LIBRARY_CACHE`) are per-process state like `CONFIG` - fine with the single worker, but another reason not to raise `--workers`. Library errors are never cached.
- Every category (instances, downloaders, indexers, media servers, transcoders) follows the same shape: a list in `config.json`, a `get_X(name)` lookup helper, a `fetch_X_status()` function, Settings UI support via the generic `parse_indexed_entries()` form parser.

## Working conventions from this project (please keep following these)

- **Verify API endpoints against real specs/responses before implementing — don't guess and ship.** Several integrations were rebuilt after guesses turned out wrong (Prowlarr's real test endpoint needed the actual OpenAPI spec; qBittorrent v5.0 renamed pause/resume to stop/start; Plex's bare API root serves XML, not its web UI). When a new integration comes up, look for the real API docs or a live response before writing the request code.
- **Real logos come from `homarr-labs/dashboard-icons`** (CDN via jsDelivr), not hand-drawn SVGs — check that project's actual catalog before assuming an icon exists in a given format (Tdarr, for example, is PNG-only there, no SVG).
- **Don't assume symmetry between similar-looking integrations.** Jellyfin/Emby share an API and both auto-redirect their bare URL to their web UI; Plex does neither of those — needs its own code paths and a `/web/index.html` suffix for direct links.
- **Jellyfin authentication changed.** Jellyfin 10.12 / 12.0 turned its legacy authorization off by default (`X-Emby-Token`, the `api_key` query parameter) and answers 401 ("CustomAuthentication was challenged" in its log) to anything but `Authorization: MediaBrowser Token="..."` / `ApiKey=`. Never build a Jellyfin/Emby header or token URL by hand: use `jellyfin_family_headers()` and `jellyfin_family_token_params()`, which send both forms to Jellyfin (older servers keep working) and only the legacy one to Emby. Found through a GitHub issue (Test button showing a bare "HTTP 401:"); not yet verified against a live Jellyfin 12 server.
- **Logging.** One logger, `arrvantage`, to stderr only (so `docker logs` / the TrueNAS Logs view; no log files), level from `LOG_LEVEL` (default WARNING; a typo falls back to WARNING). Every call to a service is recorded in one place: `_install_request_logging()` wraps `requests.Session.send`, so the ~130 request sites need no logging code - failures (HTTP >= 400, or an exception) are warnings, successes DEBUG. Never log a secret: describe a request with `describe_request()` (method, host, path - no query, no headers, no body) and pass any text that may quote a URL (a requests error does) through `scrub_log_text()`. Use `log_problem(key, ...)` for anything that can repeat (a down service is probed every few seconds): the same problem warns once per `LOG_REPEAT_SECONDS`, then drops to DEBUG. A failed sign-in logs the username only when it is a real account (people type passwords into that box). Do not log request bodies, or form data. Tests that check logging cannot use `requests_mock` - it replaces `Session.send`, which is where the hook lives - so `Tests/test_logging.py` talks to a real local HTTP server.
- **When something breaks, ask for the actual error/log output before proposing a fix.** This project's real bugs were almost always found this way (CI logs, browser DevTools Network tab, container logs) rather than guessed at.

## UI conventions

- **Shared styling lives in `static/css/`, not in templates.** `app.css` is linked by every page (login, setup, settings, dashboard) and holds only what they genuinely share: the `@font-face` rules, the design tokens (`:root` custom properties), the base reset, the one focus ring, `.sr-only`, the reduced-motion block, and `.test-btn`. `dashboard.css` is everything specific to the main dashboard. Login/setup/settings still keep their own page-specific rules in a `<style>` block.
- **Use the tokens.** Colours, spacing (`--space-*`), type sizes (`--text-*`), radii, z-layers (`--z-modal`, `--z-rail`) and motion (`--dur-fast`, `--ease-out`) are all defined in `app.css`. Don't reintroduce a copy of `:root` in a template, and don't pick a raw z-index number.
- **Link stylesheets with `asset_url('css/app.css')`**, not a bare `/static/...` path. It appends `?v=<file mtime>` so a redeployed stylesheet isn't served stale from browser cache. (The font preload is the one exception - it must match the URL inside the CSS exactly, so it stays unversioned.)
- **No inline `style=` except for values computed at runtime** (a progress bar's width, a per-instance colour, a JS-toggled `display`). Repeated styling becomes a class.
- **Status colours (green/amber/red) are reserved for status** and always come with a word or icon, never colour alone (see the disk-space "Low"/"Critically low" labels).
- **Clickable non-button elements** (cover cards, the sidebar logo) need `role="button"`/`role="link"` plus `tabindex="0"`; one delegated keydown handler in `index.html` makes Enter/Space activate them. Prefer a real `<button>` or `<a>` whenever possible.
- **Navigation structure.** Each sidebar entry is a `.nav-item` holding the tab `<button class="instance-tab">` and, beside it (never inside it), an `<a class="tab-open-link">` built by the `open_link()` macro - a link can't be nested in a button. Every view's top bar ends with the `topbar_tools()` macro (Settings, About, who's signed in + Log out); add a new view's top bar with that macro rather than copying the markup. `aria-current` is kept in sync with the `.active` class by a MutationObserver in `index.html`, so the `select*()` functions only need to toggle `.active`. The sidebar is sticky on desktop (body is `min-height`, not `height`, so it has the page to stick within) and becomes a pinned chip row on phones, where Home is a chip like the rest; `--mobile-nav-h` is the row's height, used to offset anything else that sticks to the top. Saved service URLs go through the `external_url` template filter before they become an `href`.
- **One slide-over hosts every detail view.** `#modal-overlay` > `#slide-over` (`role=dialog`, `aria-modal`) > `.modal-close` + `.modal-scroll` > `#modal-header` / `#modal-body`. Item details, `showAbout()` and `showAppearance()` all fill those two divs and add `.open` to the overlay; `closeDetails()` removes it. It slides in from the right on a desktop and up as a bottom sheet on a phone. Focus moves in on open, is trapped, and returns to the opener on close (one MutationObserver on the overlay's class - don't patch individual openers); `labelSlideOver()` points `aria-labelledby` at whichever `.modal-title` is showing. Give a new panel a `.modal-title` and nothing else is needed.
- **Themes are token sets.** A theme is a `[data-theme="key"]` block in `app.css` that restates the colour/radius/font tokens, selected by `data-theme` on `<html>` (per user, stored as `theme` on the user record, saved through `POST /api/theme`, default `midnight`, validated by `normalize_theme()`; `parse_users()` carries it forward like `home_layout`). Signed-out pages use `localStorage.arrTheme`. To add a theme: add a `THEMES` entry in `app.py` (label, description, `color` for the browser chrome) and a matching `[data-theme]` block - the Appearance picker and the tests pick it up. Components must use tokens (`--bg`, `--panel`, `--accent`, `--on-accent`, `--accent-hover`, `--hairline`, `--scrim`...), never raw colours, or they will look wrong in another theme. `auto` is a `prefers-color-scheme: light` copy of Paper, so that block must stay identical to the Paper one (a test checks it). Status colours (success/warning/error) stay reserved for status in every theme and are always paired with a word or icon; small text uses `--error-text`/`--warning` so it clears 4.5:1 on each theme's panels - run axe on a new theme. Every theme block must restate all the colour tokens itself (Midnight shares the `:root` block, which is also selected as `[data-theme="midnight"]`) because the Appearance panel previews each theme inside whichever one is active; `Tests/test_themes.py` enforces that and a 4.5:1 contrast floor for text, accent and status colours on `--bg`/`--panel` in every theme. The newer themes follow published palettes (Carbon, Nord, Solarized) with only the colours that failed contrast adjusted - say so in the block's comment.
- **Accent colour is a second, per-user choice layered on top of the theme.** `data-accent="key"` on `<html>` (stored as `accent` on the user record, saved through `POST /api/accent`, validated by `normalize_accent()`, `default` means "use the theme's own accent" and removes the key; `parse_users()` carries it forward; signed-out pages use `localStorage.arrAccent`). Each accent is a `[data-accent]` block in `app.css`, inside `@supports (color: light-dark(red, blue))`, placed after the theme blocks, using `light-dark()` so it follows each theme's `color-scheme` (Auto follows the OS). Only non-status hues are offered - green, amber and red stay reserved for status. To add one: an `ACCENTS` entry, a CSS block with accent/hover/wash/`--on-accent`, and it must pass `TestAccentContrast` (every theme's bg/panel/sidebar by scheme).
- **Warnings on Home can be hidden per user, criticals cannot.** `summarize_attention()` stays pure and user-independent (its ~30s cache is global); each item carries `hideable` and a stable `hide_key` (`queue:`, `health:`, `disk:` or `service:` prefix - extend `_HIDE_KEY_PREFIXES` for a new kind). The per-user list is `hidden_attention` on the user record, applied in the API layer by `apply_hidden_attention()` and changed through `POST /api/attention/hide` (`{key, hidden}` or `{restore_all: true}`, capped by `MAX_HIDDEN_ATTENTION`). A hidden warning stays hidden until it clears: stale keys are pruned only after a complete, error-free check (`data["complete"]`), so a flaky check never un-hides things. The sidebar dot follows what is visible. `renderAttention()` restores keyboard focus after every re-render - keep that if you change the markup.
- **Fonts are bundled** (`static/fonts/`: Geist and Geist Mono, plus IBM Plex Sans for the Carbon themes - variable woff2, split latin / latin-ext) so the UI looks the same on an offline/LAN-only install. All are SIL OFL 1.1; keep `OFL.txt` and `OFL-IBMPlexSans.txt` next to them. A theme can swap the typeface by setting `--font-sans`; the browser only downloads a font when a selected theme uses it.
- Still plain CSS with no build step - keep it that way unless there's a strong reason.
